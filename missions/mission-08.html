D+E // Deep Dive & Technical Notes

ANALYSIS NODE
D

Deep Dive Material

SQLi memiliki beberapa pola: error-based memanfaatkan pesan error, time-based blind mengamati keterlambatan response, second-order muncul ketika input berbahaya disimpan dulu lalu aktif pada proses lain, dan out-of-band melibatkan kanal terpisah secara konseptual. Dampaknya dapat berupa kebocoran data, perubahan data, bypass login, hingga pengambilalihan sistem jika digabung dengan salah konfigurasi. Mitigasi terbaik adalah prepared statement/parameterized query, validasi input, least privilege user database, ORM yang benar, dan monitoring query tidak biasa.


Hubungan offensive dan defensive: recruit belajar memahami root cause, dampak, bukti teknis, serta cara mengubah temuan menjadi rekomendasi perbaikan.

O // Textbook Chapter

DEEP MATERIAL NODE
FULL CHAPTER MODE

SQL Injection: Batas antara Data dan Perintah

Bab ini membahas SQL Injection secara aman dan defensif. Fokusnya adalah memahami mengapa input user tidak boleh dicampur dengan query mentah, bagaimana dampaknya terhadap database, dan bagaimana prepared statement mencegah kelas masalah ini.

Query database dan sumber risiko

Aplikasi web sering menerima input lalu memakai input tersebut untuk mengambil data dari database. Risiko muncul ketika input user digabung langsung ke string SQL. Dalam kondisi itu, database dapat gagal membedakan bagian mana yang merupakan data biasa dan bagian mana yang merupakan instruksi. SQL Injection terjadi karena batas antara data dan perintah rusak.

SQL Injection bukan sekadar “mengetik karakter aneh”. Ia adalah kegagalan desain query. Jika aplikasi membangun query dengan concatenation string, attacker di lab dapat memengaruhi struktur query. Dampaknya dapat berupa bypass autentikasi, membaca data sensitif, memodifikasi data, menghapus data, atau dalam konfigurasi tertentu memengaruhi sistem lain. Dalam pembelajaran etis, pembuktian harus dilakukan hanya pada lab seperti PortSwigger Academy, DVWA, Juice Shop, atau aplikasi lokal sendiri.

Jenis gejala SQLi

Dalam error-based SQLi, aplikasi menampilkan error database yang memberi petunjuk. Dalam blind SQLi, aplikasi tidak menampilkan data langsung, tetapi perilaku response berubah berdasarkan kondisi. Dalam time-based blind, perbedaan waktu response menjadi sinyal. Second-order SQLi lebih rumit karena input berbahaya disimpan dulu, lalu baru memengaruhi query di proses lain. Dari sisi pembelajaran, yang penting adalah memahami gejala, bukan menghafal payload.

Mitigasi utama: parameterized query

Pencegahan paling penting adalah prepared statement atau parameterized query. Dengan parameterized query, struktur SQL ditentukan terlebih dahulu, dan input user dikirim sebagai nilai parameter. Database tidak menafsirkan parameter sebagai instruksi SQL. ORM dapat membantu, tetapi ORM tidak otomatis aman jika developer tetap menyusun raw query dari string input.

Kontrol tambahan meliputi validasi input sesuai tipe data, least privilege untuk akun database, tidak menampilkan error database ke user, logging query gagal secara aman, dan monitoring pola request anomali. Akun database aplikasi tidak seharusnya memiliki privilege administratif jika hanya perlu membaca/menulis tabel tertentu.

Deteksi dari sisi defender

Defender mencari pola seperti error database berulang, parameter dengan karakter tidak lazim, response 500 meningkat, query lambat tidak biasa, atau WAF/IDS alert. Namun deteksi bukan pengganti perbaikan kode. WAF dapat membantu menahan pola umum, tetapi akar masalah tetap harus diselesaikan dengan parameterized query.

Skenario lapangan

Sebuah fitur pencarian peserta menggabungkan keyword langsung ke query. Pada staging, tester legal menemukan input tertentu menyebabkan error database. Laporan tidak perlu mengekstrak data nyata. Cukup tunjukkan bahwa query dapat dipengaruhi, jelaskan dampak potensial, sertakan lokasi kode rentan, lalu rekomendasikan prepared statement, validasi tipe, dan pembatasan privilege database.
