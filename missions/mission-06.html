D+E // Deep Dive & Technical Notes

ANALYSIS NODE
D

Deep Dive Material

Broken authentication sering muncul dari password policy lemah, reset password buruk, tidak ada rate limit, session token tidak aman, atau MFA tidak diterapkan. Broken access control muncul ketika validasi hanya dilakukan di frontend, endpoint tidak mengecek role, atau objek bisa ditebak. Race condition dan captcha bypass perlu dipahami sebagai risiko desain, namun praktik harus dibatasi pada lab legal. Mitigasi utama: cek akses server-side, least privilege, session expiration, token kuat, audit log, MFA, dan rate limiting.


Hubungan offensive dan defensive: recruit belajar memahami root cause, dampak, bukti teknis, serta cara mengubah temuan menjadi rekomendasi perbaikan.

O // Textbook Chapter

DEEP MATERIAL NODE
FULL CHAPTER MODE

Broken Authentication, Session Management, IDOR, dan Broken Access Control

Bab ini membahas identitas dan otorisasi. Banyak insiden terjadi bukan karena algoritma kriptografi rusak, tetapi karena aplikasi gagal memastikan siapa usernya dan apa yang boleh dilakukan user tersebut.

Authentication berbeda dari authorization

Authentication menjawab “siapa kamu?”. Authorization menjawab “apa yang boleh kamu akses?”. User yang berhasil login belum tentu boleh melihat semua data. Banyak celah muncul ketika developer hanya memeriksa apakah user sudah login, tetapi tidak memeriksa apakah user tersebut pemilik data atau memiliki role yang sesuai.

Broken authentication dapat terjadi karena password policy lemah, tidak ada rate limiting, session tidak kedaluwarsa, reset password tidak aman, MFA tidak diterapkan pada akun penting, atau token mudah ditebak. Broken session management terjadi ketika session identifier dapat dipakai terlalu lama, tidak dirotasi setelah login, tidak invalid saat logout, atau cookie tidak diberi atribut keamanan.

IDOR dan broken access control

IDOR atau Insecure Direct Object Reference terjadi ketika aplikasi menggunakan identifier objek secara langsung dan tidak memeriksa kepemilikan/otorisasi di server. Misalnya, endpoint legal di lab mengembalikan invoice berdasarkan ID. Jika user A dapat mengganti ID dan melihat invoice user B, masalahnya bukan sekadar angka ID yang mudah ditebak, tetapi tidak adanya server-side authorization check.

Broken access control lebih luas. Bentuknya dapat berupa user biasa mengakses halaman admin, API menerima role dari client, endpoint backend tidak dilindungi karena tombol UI disembunyikan saja, atau policy role tidak konsisten antar fitur. UI bukan kontrol keamanan. Semua keputusan akses harus divalidasi di server.

Risiko dan dampak

Dampaknya bisa sangat besar: pengambilalihan akun, kebocoran data pribadi, transaksi tidak sah, eskalasi privilege, manipulasi data, dan pelanggaran regulasi. Dalam organisasi, celah akses sering menjadi temuan prioritas tinggi karena menyerang inti kepercayaan aplikasi: data user harus tetap milik user tersebut.

Deteksi dan pencegahan

Defender mencegah dengan MFA, rate limiting, lockout adaptif, password hashing yang kuat, cookie secure, session expiration, token rotation, dan server-side authorization pada setiap request. Access control harus diuji dengan matriks role: user biasa, admin, owner data, guest, dan service account. Logging harus mencatat login gagal berulang, perubahan role, akses ke objek sensitif, dan percobaan akses ditolak.

Deteksi IDOR membutuhkan korelasi. Jika akun user biasa mengakses banyak objek milik user lain dalam waktu singkat, itu sinyal anomali. Namun sistem harus dirancang agar request tersebut ditolak sejak awal, bukan hanya terdeteksi setelah terjadi.

Skenario lapangan

Dalam aplikasi e-learning, user login dapat melihat sertifikatnya sendiri. Pentester pada staging menemukan bahwa endpoint sertifikat hanya memeriksa “sudah login”, bukan “pemilik sertifikat”. Laporan yang baik tidak menampilkan data nyata berlebihan; cukup bukti minimal, dampak, endpoint, kondisi, dan rekomendasi: tambahkan ownership check di server, audit log akses sertifikat, dan test otomatis untuk semua role.
